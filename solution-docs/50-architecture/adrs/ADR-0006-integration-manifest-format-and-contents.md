# ADR-0006: Integration Manifest Format and Contents

**Status:** Proposed
**Date:** 2026-07-26
**Owners:** Product lead, technical lead
**Related agreements:** [AGR-019](../../00-source-of-truth/AGREEMENTS.md#agr-019--meaning-of-import), [AGR-002](../../00-source-of-truth/AGREEMENTS.md#agr-002--three-deployment-modes), [AGR-005](../../00-source-of-truth/AGREEMENTS.md#agr-005--policy-portability), [AGR-006](../../00-source-of-truth/AGREEMENTS.md#agr-006--one-logical-evaluation-contract-across-all-modes), [AGR-011](../../00-source-of-truth/AGREEMENTS.md#agr-011--observe-before-enforce-progression), [AGR-017](../../00-source-of-truth/AGREEMENTS.md#agr-017--core-domain-model), [AGR-018](../../00-source-of-truth/AGREEMENTS.md#agr-018--trust-and-enforcement-model)
**Related ADRs:** depends on [ADR-0005](./ADR-0005-evaluation-contract-wire-format.md) (the endpoint and contract version a manifest points at)

While this ADR reads `Proposed` it binds no one.

## Context

[AGR-019](../../00-source-of-truth/AGREEMENTS.md#agr-019--meaning-of-import) defines "import" as a consuming team adopting *"a versioned guardrail policy, a workload identity, an **integration manifest**, a connector configuration, and an enforcement mode,"* and names the seven-step onboarding flow — register workload → select policy → **generate integration manifest** → install connector → observe → review → enforce — as the canonical reference implementation of the term.

That phrase is load-bearing. "Integration manifest" appears in the charter, the product overview, the value proposition, the use cases, the security architecture, the glossary, the claims register, the implementation strategy, the executive expected-outcomes register ([EO-B1](../../30-executive/EXPECTED-OUTCOMES.md)), and the sales narrative. [`USE-CASES.md` UC-002](../../20-product/USE-CASES.md) states that at this step *"the platform produces the connector configuration for that binding."*

**No document says what a manifest is.** There is no format, no field list, no statement of whether it is a file or a screen, no rule for what it must never contain, and no owner for generating it.

Three consequences follow, and all three are live:

- **An executive-register output is unverifiable.** EO-B1 commits to *"onboarding flow implemented end to end,"* with "generate integration manifest" as an explicit step. There is no way to demonstrate that step is complete, because there is no artifact to point at.
- **AGR-019's prohibitions are unenforceable.** The agreement says the import process must never require copying another team's LiteLLM database, transferring model-provider credentials, exposing gateway administration endpoints, replacing model-routing configuration, or granting administrative access. Those are constraints on *what the manifest carries* — and an artifact with no defined contents cannot be checked against them. The strongest trust commitment in the product currently rests on an undefined object.
- **Every client will invent its own.** The LiteLLM connector, the generic SDK, and a consumer-operated custom gateway ([AGR-003](../../00-source-of-truth/AGREEMENTS.md#agr-003--litellm-as-first-connector-not-the-product-boundary)) each need to be configured at onboarding. Three authors will make the same undocumented choices, differently — the same failure [ADR-0005](./ADR-0005-evaluation-contract-wire-format.md) found in the evaluation contract, one step earlier in the flow.

The question this ADR resolves: **what is an integration manifest, what must it carry, and what must it never carry?**

## Decision

### 1. The manifest is a file, not a screen

The manifest is a **machine-readable, version-controllable artifact** that a consuming team receives, commits to its own repository, reviews, and diffs. It is not a rendered page, a copy-paste snippet, or a set of console instructions.

This is what makes a setup shareable: one team can hand another its manifest, a manifest can be reviewed in a pull request alongside the change that installs the connector, and a drifted configuration is visible as a diff rather than as a support conversation.

**Format is YAML**, schema-validated, with the schema published alongside the policy schema. YAML because the policy artifact it accompanies is authored the same way, and because a consuming team is expected to read and review this file, not only feed it to a tool.

### 2. The manifest is derived, never authoritative

A manifest is **generated by the control plane from an existing policy binding**. It is a rendering of state the platform already holds ([AGR-017](../../00-source-of-truth/AGREEMENTS.md#agr-017--core-domain-model): Tenant, Workload, Policy, Policy binding), not a new source of truth.

Consequences of that, all deliberate:

- A manifest is **regenerable**. Losing one is an inconvenience, never an outage.
- A manifest is **not authoritative at evaluation time**. The runtime resolves the effective policy and mode server-side regardless of what any manifest says, exactly as [ADR-0005](./ADR-0005-evaluation-contract-wire-format.md) makes `policy_ref` advisory. A team cannot obtain weaker enforcement by editing its manifest.
- A manifest **can go stale**, and must say which binding and generation it came from so staleness is detectable rather than silent.

### 3. Required contents

A manifest must carry, at minimum:

| Element | Why it is present |
|---|---|
| Manifest schema version | Changes to this artifact are versioned; see §6 |
| Tenant identifier and workload identity | The identity every evaluation, binding, and audit record resolves to ([CON-011](../../00-source-of-truth/CONSTRAINTS.md#con-011--per-tenant-workload-identities)) |
| Policy name and immutable policy version | What the workload is bound to, recorded so a reviewer sees it without querying the platform |
| Enforcement mode | Observe or enforce — the observe-before-enforce state is part of what is adopted (AGR-019, [AGR-011](../../00-source-of-truth/AGREEMENTS.md#agr-011--observe-before-enforce-progression)) |
| Deployment mode and Evaluation API endpoint | Which of the three modes ([AGR-002](../../00-source-of-truth/AGREEMENTS.md#agr-002--three-deployment-modes)) this workload operates under, and where its runtime is |
| Evaluation contract major version | The `/vN` surface the connector must speak ([ADR-0005](./ADR-0005-evaluation-contract-wire-format.md) §2) |
| Connector type and supported connector version range | Derived from the workload's `gateway type` attribute; makes an incompatible connector a detectable condition rather than a runtime surprise |
| Per-stage evaluation timeouts | Required to be explicit and never an undocumented default ([CON-016](../../00-source-of-truth/CONSTRAINTS.md#con-016--timeout-limits)) |
| Client-side failure behavior | What the client does when the runtime is unreachable. An unset value is a configuration error, never a silent allow ([AGR-012](../../00-source-of-truth/AGREEMENTS.md#agr-012--failure-behavior-is-part-of-policy)) |
| Required runtime capabilities | The evaluator capabilities the bound policy needs, so an unsatisfiable setup fails at bind time rather than degrading in production |
| Correlation-identifier propagation requirement | A connector responsibility (seed.md §12) that a manifest must state rather than assume |
| Source binding reference and generation timestamp | Makes staleness detectable |

### 4. Prohibited contents — the AGR-019 enforcement point

A manifest **must never contain**:

- Model-provider credentials, or any reference that would require transferring them
- Gateway administration endpoints or credentials
- Any part of a consuming team's model-routing configuration
- Any reference requiring access to a consuming team's LiteLLM database
- Any AI Guardrails platform secret, signing key, or long-lived bearer credential

This list is a restatement of [AGR-019](../../00-source-of-truth/AGREEMENTS.md#agr-019--meaning-of-import) expressed as a property of a concrete artifact, which is what makes it checkable: the manifest schema forbids these fields, and a validation check over generated manifests enforces the agreement mechanically rather than by review discipline.

### 5. A manifest is not a credential

The workload identity a manifest carries is an **identifier, not a secret**. Authentication to the Evaluation API is IAM/SigV4 ([CON-010](../../00-source-of-truth/CONSTRAINTS.md#con-010--iam-based-authentication-and-least-privilege-roles), [`SECURITY-ARCHITECTURE.md` §5](../SECURITY-ARCHITECTURE.md)); possession of a manifest grants nothing.

This is load-bearing rather than incidental. If a manifest were a secret it could not be committed to a repository, reviewed in a pull request, or handed between teams — and the shareability that motivates §1 would be lost. Any future proposal to embed a credential in a manifest is a proposal to make it unshareable, and must be recorded as such.

### 6. Versioning

The manifest schema carries its own version, independent of the evaluation contract version, the policy version, and the product version. It changes under the same classification rules [ADR-0005](./ADR-0005-evaluation-contract-wire-format.md) §2 applies to the evaluation contract: additive optional fields are minor; removals, renames, narrowed validation, and changed meanings are major.

### 7. One manifest shape across all three modes

The same manifest structure serves Remote Evaluation, Guarded Gateway, and Customer-Managed Runtime. What differs between modes is the **value** of the endpoint and deployment-mode fields, never the shape of the artifact.

This mirrors [AGR-006](../../00-source-of-truth/AGREEMENTS.md#agr-006--one-logical-evaluation-contract-across-all-modes) one level up the stack: if adopting a policy under Mode C required a structurally different manifest than under Mode A, "one logical contract across all modes" would hold for evaluation while breaking for onboarding, and the mode-portability claim would be true only of the part nobody integrates against first.

## Scope boundaries

This ADR does **not** decide:

- **Whether a policy catalog user interface is built, or in which phase.** A full administration portal is a named non-goal for Phases 1–2 ([`SCOPE.md` §6](../../10-charter/SCOPE.md#6-delivery-non-goals-phases-12), seed.md §17). This ADR defines the artifact such a surface would generate; the surface itself is out of scope here. Manifest generation is API-first precisely so a later UI is one consumer of it rather than the only way to obtain one.
- **Whether "select policy" means one policy or a composed set.** Bindings today associate one workload with exactly one policy version. Multi-policy selection is policy composition, tracked as [OQ-021](../../00-source-of-truth/OPEN-QUESTIONS.md#oq-021--policy-selection-cardinality-in-the-onboarding-flow) and dependent on [OQ-012](../../00-source-of-truth/OPEN-QUESTIONS.md#oq-012--policy-signing-and-policy-inheritance-design).
- **The connector installation mechanism.** What a team does *with* a manifest — package manager, container image, configuration reload — is a connector concern, not a manifest concern.
- **Authentication topology**, which [`SECURITY-ARCHITECTURE.md` §5](../SECURITY-ARCHITECTURE.md) owns.

## Alternatives considered

- **Alternative: the manifest is a screen — onboarding renders instructions the team copies.**
  **Why not chosen:** Not shareable, not reviewable, not diffable, and it cannot be checked against AGR-019's prohibitions because there is no artifact to check. It also makes configuration drift invisible: a team that changed its endpoint by hand months ago is indistinguishable from one that did not. The onboarding flow is explicitly described as a repeatable sequence, not a one-time console visit ([`CLAIMS-REGISTER.md`](../../70-governance/CLAIMS-REGISTER.md)).

- **Alternative: a bespoke manifest per connector type.**
  **Why not chosen:** Produces three artifacts to version, three schemas to validate, and three places for the AGR-019 prohibitions to be enforced inconsistently. Connector type is a *field* in one manifest, not a reason for three manifests.

- **Alternative: embed a workload credential so the manifest is self-sufficient.**
  **Why not chosen:** Contradicts [CON-010](../../00-source-of-truth/CONSTRAINTS.md#con-010--iam-based-authentication-and-least-privilege-roles) (IAM-based authentication) and destroys the property that motivates the artifact — a secret-bearing file cannot be committed, reviewed, or shared, which is most of its value.

- **Alternative (chosen): a generated, schema-validated, secret-free YAML file, derived from a binding, one shape across all three modes, with an explicit prohibited-contents list.**
  **Why accepted:** Makes an executive-register output demonstrable, makes the product's strongest trust commitment mechanically checkable, gives the three client authors one specification instead of three guesses, and leaves a later catalog UI as an additional surface over the same generator rather than a redesign.

## Consequences

### Positive

- AGR-019 becomes enforceable rather than aspirational: the prohibitions are schema constraints on a named artifact, checkable in CI.
- EO-B1's "generate integration manifest" step becomes demonstrable — there is an artifact to produce and inspect.
- A consuming team can commit its manifest, review it in a pull request, and hand it to another team. "Shareable setup" becomes a property of the design rather than a hope.
- A future policy-catalog surface — *"choose a policy, then show me how to integrate it for my stack"* — is a renderer over this artifact plus the workload's existing `gateway type` and `deployment mode` attributes. No new domain data is required for it, which is why it can be sequenced later without stranding this decision.
- Manifest staleness becomes detectable, because the artifact records the binding and generation it came from.

### Negative

- One more versioned artifact to maintain, with its own schema and compatibility discipline.
- Generation must be available in every environment where onboarding happens, including Mode C customer environments where the control plane may be reachable only intermittently.
- A committed manifest is a second place a policy version appears, so a rolled-back binding leaves stale manifests in consuming repositories. Mitigated by §2 (the runtime resolves server-side and ignores the manifest's assertion), but the stale file will still confuse a reader.

### Risks

- **A manifest is treated as authoritative by an implementer**, so a team believes editing it changes enforcement. This is the most dangerous misreading; mitigated by §2 and by the runtime resolving policy server-side regardless.
- **The prohibited-contents list decays** as fields are added for convenience, until a credential arrives "just for this connector." Mitigated by making the list a schema constraint and a validation check rather than prose in a document.
- **The manifest becomes a de facto configuration API**, accumulating deployment settings that belong to the consuming team's own infrastructure. Mitigated by §3 being a minimum *and* a boundary: additions require a recorded decision.

## Validation required

This ADR is validated when:

1. A manifest schema is published, and a generated manifest for a real binding validates against it.
2. A validation check demonstrably fails a manifest containing any prohibited element from §4.
3. The same workload, bound under Remote Evaluation and then under Customer-Managed Runtime, produces manifests differing only in endpoint and deployment-mode values (§7).
4. A manifest generated for a policy whose required capabilities the target runtime cannot serve is refused at binding time, not emitted.
5. [`USE-CASES.md` UC-002](../../20-product/USE-CASES.md) step 3 and [`AGREEMENTS.md` AGR-019](../../00-source-of-truth/AGREEMENTS.md#agr-019--meaning-of-import) cite this ADR as the definition of the artifact they name.
